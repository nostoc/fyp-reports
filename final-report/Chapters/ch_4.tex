\section{Introduction}
\label{sec:implementation-introduction}

This chapter explains how the design in Chapter~\ref{ch:architecture} is implemented. The blockchain, smart contracts, identity simulator, relayer, AI services, IPFS service, and web clients are described. Only implemented behaviour is presented. The identity component is described as a simulator, and the AI component is described as an off-chain aggregator rather than a decentralized oracle network.

\section{Private PoA Implementation}
\label{sec:poa-implementation}

The private blockchain is implemented with Geth version 1.13.15 and Clique Proof-of-Authority consensus. The genesis configuration sets chain ID 1337 and a block period of five seconds. Three sealer addresses are placed in the Clique \texttt{extraData} field.

Four Geth nodes are configured. Nodes 1, 2, and 3 run with block sealing enabled and use separate validator accounts. Node 4 does not run with block sealing enabled. It exposes the HTTP JSON-RPC endpoint on port 8545 and is used by application services. The nodes use network ID 1337 and fixed peer addresses. The RPC node is therefore separated from the three consensus participants.

The network is private and permissioned. Clique gives predictable confirmation time for the prototype, but its safety depends on the operation of the known validators. It is not presented as public-chain decentralization.

\section{Smart Contract Implementation}
\label{sec:contract-implementation}

Four contracts are deployed: \texttt{Reporting}, \texttt{EmergencyReporting}, \texttt{AuthorityMultiSig}, and \texttt{OpinionPolling}. The source files use Solidity pragma \texttt{\string^0.8.20}. The current Hardhat configuration compiles with Solidity 0.8.28, the London EVM target, optimization, and the intermediate-representation pipeline.

\subsection{Reporting Contract}
\label{subsec:reporting-contract}

The Reporting contract stores standard civic reports. Each report includes an ID, IPFS CID, report hash, submission nullifier, citizen pseudonym, relayer address, status, timestamps, phase deadline, assigned authority, vote counters, latest authority comment, and latest authority image CID. A separate append-only mapping stores the full authority action history.

The following eight statuses are implemented:

\begin{quote}
\texttt{PendingValidation}, \texttt{CommunityRejected}, \texttt{Open},
\texttt{InProgress}, \texttt{PendingRejectionReview},
\texttt{PendingVerification}, \texttt{Closed}, and \texttt{Reopened}.
\end{quote}

Standard submissions are created as \texttt{PendingValidation}. The default voting window is six hours. Four voting methods are available: simple majority, two-thirds supermajority, minimum threshold, and a hybrid of two methods. The simple-majority method is selected by default.

Mappings are maintained for used submission nullifiers and for used vote nullifiers in validation, verification, and rejection-review phases. Citizen pseudonym mappings also prevent one pseudonym from voting twice in the same phase. Validation revotes are limited to quorum-failure cases and are capped at three cycles.

Authorized relayers submit reports and votes. Authorized authorities start work, add updates, mark reports as solved, and reject reports. Status checks are made before each change. OpenZeppelin ownership and reentrancy protection are used.

\subsection{EmergencyReporting Contract}
\label{subsec:emergency-contract}

The EmergencyReporting contract stores urgent reports separately. A valid emergency submission is created directly as \texttt{Open}; community validation is not performed first. The four emergency statuses are \texttt{Open}, \texttt{InProgress}, \texttt{Resolved}, and \texttt{Reclassified}.

An emergency can be resolved from \texttt{Open} or \texttt{InProgress}. A false emergency can be reclassified. When reclassification is recorded, the citizen pseudonym is blocked from new emergency submissions for 30 days:

\begin{equation}
    T_{\mathrm{unlock}} = T_{\mathrm{block}} + 30 \times 24 \times 60 \times 60,
    \label{eq:emergency-penalty}
\end{equation}

where \(T_{\mathrm{unlock}}\) is the unlock time and \(T_{\mathrm{block}}\) is the current block timestamp in seconds.

\subsection{AuthorityMultiSig Contract}
\label{subsec:multisig-contract}

The AuthorityMultiSig contract manages Super Admins, authority workers, profiles, and voting configuration. A proposal is created for adding or removing a Super Admin, adding or removing an authority worker, or changing the standard-report voting method. The proposer automatically gives the first approval.

The required approval count is recalculated from the current Super Admin count by Equation~\ref{eq:governance-quorum}. A proposal is executed when its yes-vote count reaches this strict majority. Authority changes are sent to the Reporting contract and, when configured, to the EmergencyReporting contract. The Reporting contract is owned by the multisig contract after deployment, so governed calls can change its protected configuration.

\subsection{OpinionPolling Contract}
\label{subsec:polling-contract}

The OpinionPolling contract stores a poll ID, creator, IPFS metadata CID, deadline, poll type, and active flag. True/false and multi-choice polls are supported. Poll creation is limited to an address that is authorized by the Reporting contract.

Vote counts are stored by poll ID and option index. A mapping from poll ID and nullifier to a Boolean value prevents the same nullifier from being used twice in one poll. The contract records counts only; it does not implement a zero-knowledge voting proof.

\section{Citizen Identity Simulator}
\label{sec:identity-simulator-implementation}

The identity service is implemented with Node.js, Express, ethers.js, and a simulated citizen database. A government ID and password are checked against an active simulated record. After successful checking, a configurable batch of ticket IDs is created. The default batch size is ten.

For each ticket, a UUID is generated and hashed with \texttt{ethers.id}. The resulting 32-byte ticket ID is signed by the configured government wallet. The signed ticket and its issue record are stored by the simulator. A previously assigned citizen seed is also returned.

The dApp derives a citizen private key by hashing the citizen seed together with a configured wallet salt. An Ethereum wallet is created from the result. This process gives the same wallet for the same seed and salt.

This implementation is not a real zero-knowledge proof. The simulator directly verifies the government ID and password. Government-signed tickets are later used as one-use nullifiers. They do not prove an identity statement through zero knowledge. Integration with a real anonymous credential or zero-knowledge system is left as future work.

\section{Relayer Cryptography and Queue Processing}
\label{sec:relayer-queue-implementation}

The backend relayer is implemented with NestJS and ethers.js. Citizen-facing blockchain writes are submitted through this service. Three checks are made before a report is queued.

\begin{enumerate}
    \item The government signature is recovered from the ticket ID and is compared with the configured government address.
    \item Each uploaded image is hashed with Keccak-256 and is compared with the corresponding hash supplied by the dApp.
    \item The composite report hash is rebuilt according to Equation~\ref{eq:report-hash}. The citizen signature is recovered and is compared with the supplied citizen wallet address.
\end{enumerate}

After these checks, the citizen pseudonym is derived according to Equation~\ref{eq:pseudonym}. Image buffers are converted to base64 before queue storage so that they can pass through Redis.

A BullMQ flow contains three ordered child jobs. The AI moderation job is run first, the IPFS upload job is run second, and the blockchain submission job is run third. The AI step has one attempt because a moderation rejection is treated as a final decision. The IPFS and blockchain steps allow three attempts. A failed child is configured to fail its parent flow.

The HTTP response contains a job ID without waiting for all three steps. Progress objects are emitted inside the relayer and are sent through an SSE endpoint. Each SSE stream is filtered by the citizen wallet address. A separate vote queue is used for citizen vote transactions.

\section{AI Moderation Implementation}
\label{sec:ai-implementation}

The AI component is implemented as one decision aggregator and three classifier services: safety, spam, and civic relevance. These services run off-chain. They are not blockchain validators, and they do not form a decentralized oracle network.

\subsection{Request Protection and Aggregation}
\label{subsec:ai-aggregation}

The relayer sends a moderation request with an API key, relayer signature, timestamp, and random nonce. A canonical request object is hashed and signed by the relayer. The aggregator recovers the signer address and compares it with the trusted relayer address. The timestamp is checked against a configurable maximum age. Used nonces are stored in SQLite and are rejected on reuse.

Each classifier is called by the aggregator. A service error or unavailable service produces a rejection result. Safety rejection, civic-relevance rejection, spam rejection, or any critical violation causes a final rejection. Otherwise, acceptance requires at least two accept votes and no reject vote. The implementation is therefore fail-closed. The returned decision contains hashes and an optional aggregator signature, but this off-chain decision is not blockchain consensus.

\subsection{Safety Service}
\label{subsec:safety-service}

Text safety is checked with \texttt{unitary/toxic-bert}. The first 512 characters are passed to the model pipeline. The implemented unsafe thresholds are shown in Table~\ref{tab:safety-thresholds}.

    \caption{Implemented Toxic-BERT thresholds}
    \label{tab:safety-thresholds}
    \small
    \begin{tabular}{|l|c|l|}
        \hline
        \textbf{Label} & \textbf{Threshold} & \textbf{Critical} \\
        \hline
        \texttt{toxic} & 0.50 & No \\
        \hline
        \texttt{severe\_toxic} & 0.50 & Yes \\
        \hline
        \texttt{obscene} & 0.60 & No \\
        \hline
        \texttt{threat} & 0.40 & Yes \\

        \hline

Image safety is checked with \texttt{Falconsai/nsfw\_image\_detection}. The maximum score for the labels \texttt{nsfw}, \texttt{porn}, \texttt{sexy}, and \texttt{hentai} is used. An image is rejected when this score is at least 0.70.

Accepted images are processed for faces with OpenCV Haar cascades. Frontal, alternative frontal, left-profile, and mirrored right-profile checks are used. Overlapping boxes are reduced, and Gaussian blur is applied to detected face areas. The processed images are returned to the relayer for IPFS storage.

\subsection{Spam Service}
\label{subsec:spam-service}

Spam is checked with \texttt{mrm8488/bert-tiny-finetuned-sms-spam-detection} and a rule score. The default thresholds are 0.85 for a strong model rejection, 0.65 for model support, 0.60 for a rule-only rejection, and 0.25 for rule support.

Rules add scores for very short text, known spam phrases, promotional words, URLs, repeated characters, and excessive symbols. The final rule score is capped at 1.0. A report is rejected when the model is strongly confident, when the rule score reaches the rejection threshold, or when both supporting thresholds are reached.

\subsection{Civic Relevance Service}
\label{subsec:civic-service}

Text relevance is checked with \texttt{sentence-transformers/all-MiniLM-L6-v2}. Normalized text embeddings are compared with precomputed reference embeddings by cosine similarity. The reference set covers common local issues and a general civic category.

The default text relevance threshold is 0.38. A lower maximum similarity causes rejection. The selected-category match threshold is 0.40. A category mismatch produces an explanation but does not reject text that is otherwise civic.

CLIP-based image relevance is disabled and is not evaluated in this implementation. Images are checked for safety, but an image-to-civic-category relevance claim is not made.

\section{IPFS Implementation}
\label{sec:ipfs-implementation}

The IPFS layer contains an IPFS node and an Express HTTP service. For a complaint upload, description, category, and location are required. Up to five images are accepted by the storage endpoint. Each image entry contains its original name, MIME type, byte size, and base64 data.

One JSON envelope is formed with the following fields:

\begin{quote}
\texttt{type}, \texttt{description}, \texttt{category}, \texttt{location},
\texttt{imageCount}, \texttt{images}, and \texttt{storedAt}.
\end{quote}

The complete envelope is added and pinned as one IPFS object with CID version 1. One CID is returned for both metadata and images. If blurred images are returned by the safety service, they replace the original buffers before this envelope is uploaded.

No authentication is implemented at the IPFS HTTP service level. CORS and HTTP security headers are present, but they do not authenticate clients. The service is therefore assumed to be protected by network isolation. This assumption is a deployment limit, not a production security control.

\section{Web Client Implementation}
\label{sec:web-client-implementation}

The main citizen and authority dApp is implemented with Next.js, React, Tailwind CSS, and ethers.js. Citizens can authenticate through the simulator, submit standard or emergency reports, follow queue progress, read reports, vote, and view their own pseudonymous reports. Authorities can view actionable reports, post updates, submit results, and use governance and polling functions.

Direct blockchain reads are made through a JSON-RPC provider. Citizen writes are sent to the relayer so that citizens do not need gas or direct wallet transaction handling. Authority and Super Admin actions are signed through MetaMask.

The citizen wallet is derived from the citizen seed. Session data can optionally be protected by a user PIN. The browser uses PBKDF2 with SHA-256 and 600,000 iterations to derive a 256-bit key, and AES-GCM is used for encryption. A random 16-byte salt and 12-byte initialization vector are stored with the ciphertext. This protects stored session data when the feature is used, but a weak PIN can still be guessed.

A separate Vite and React portal is implemented for the government identity simulator. It is kept separate from the public dApp because it represents a different administrative boundary.

\section{Deployment and Configuration}
\label{sec:deployment-configuration}

Services are containerized and are configured through environment variables. Blockchain configuration includes RPC URLs, contract addresses, chain ID, and relayer keys. Relayer configuration includes the government address, pseudonym salt, Redis connection, AI endpoint, API key, and IPFS endpoint. AI configuration includes trusted relayer details, model switches, thresholds, request age, nonce database path, and worker URLs.

The Geth nodes are connected on a private network. The AI workers communicate with the aggregator through an internal service network. The IPFS HTTP endpoint is expected to be isolated because application-level authentication is absent.

Optional Planka workforce tracking is feature-flagged through deployment configuration. When it is disabled or not configured, the blockchain workflow continues without it. When it is enabled, report status events can be mirrored to Planka cards. Planka is not a source of truth for report status.

Secrets such as private keys, API keys, Redis passwords, government signing keys, and PIN-derived session keys must not be committed to source control. Separate values are required for development and deployment.

\section{Implementation Constraints}
\label{sec:implementation-constraints}

The current implementation has the following limits.

\begin{enumerate}
    \item The identity service is a simulator. Government ID and password values are directly checked, so production-grade zero knowledge is not provided.
    \item Ticket nullifiers reduce repeated use, but privacy still depends on the simulator, relayer, browser, and stable pseudonym design.
    \item Category and location are stored in the IPFS envelope but are not covered by the implemented citizen composite hash.
    \item The AI models can produce false acceptance and false rejection. Model fallback rules also have limited language and context coverage.
    \item CLIP image relevance is disabled and is not evaluated.
    \item The AI aggregator is centralized off-chain. Its signature does not make the classifier services a decentralized oracle network.
    \item The IPFS HTTP service has no application-level authentication and depends on network isolation.
    \item Base64 images increase the size of the single complaint envelope. Large envelopes can increase storage and transfer cost.
    \item The private PoA network has only three validators. Its availability and independence depend on those operators.
    \item Browser storage, deterministic wallet derivation, and optional PIN protection require stronger recovery and device-security measures before production use.
    \item Planka synchronization is optional and can become inconsistent with the blockchain if external requests fail.
\end{enumerate}

\section{Summary}
\label{sec:implementation-summary}

This chapter describes the implemented private Geth Clique network, four smart contracts, identity simulator, relayer, BullMQ pipeline, AI moderation services, IPFS envelope, and web clients. The system uses government-signed one-use ticket IDs as nullifiers and uses pseudonymous citizen wallets. Its important limits are stated: no real zero-knowledge proof is implemented, no decentralized oracle network is claimed, CLIP relevance is not evaluated, and IPFS service security depends on network isolation.
