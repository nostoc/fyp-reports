\section{Private PoA Implementation}
\label{sec:poa-implementation}

The private blockchain is implemented with Geth version 1.13.15 and Clique Proof-of-Authority consensus. Pinning a specific Geth version keeps the genesis format and consensus behaviour consistent across every developer machine and deployment host, avoiding version-dependent inconsistencies. The genesis configuration sets chain ID 1337 and a block period of five seconds. Three sealer addresses are placed in the Clique extraData field so that only those three accounts are recognised as authorized block producers from the very first block.

Four Geth nodes are configured, as shown in Figure~\ref{fig:poa-node-configuration}. Nodes 1, 2, and 3 run with block sealing enabled and use separate validator accounts, matching the three sealer addresses fixed in the genesis file. Node 4 does not run with block sealing enabled. Instead, it exposes the HTTP JSON-RPC endpoint on port 8545 and is used by application services. Keeping sealing and RPC serving on different nodes ensures that request traffic from the \ac{DApp} and the relayer is handled entirely by Node 4. Therefore, it cannot add load to, or interfere with the three nodes that are actually reaching consensus. All four nodes share network ID 1337 and fixed peer addresses, so the RPC node stays synchronized with the sealing validators without needing to participate in sealing itself.

    \centering

    \caption{Node and port configuration of the private Geth Clique PoA network}

The network is private and permissioned, which was chosen because Clique gives predictable confirmation time for a citizen-facing reporting workload, and a small known validator set is enough during a prototype phase.


\section{Citizen Identity Simulator}
\label{sec:identity-simulator-implementation}

The identity service is implemented with Node.js, Express, ethers.js, and a simulated citizen database. It matches the JavaScript-based stack used elsewhere in the project so the same signing and hashing utilities can be reused. A government ID and password are checked as shown in Figure~\ref{fig:citizen-login} against an active simulated record. After successful checking, a configurable batch of ticket IDs is created as shown in Figure~\ref{fig:citizen-seed-ticket-batch}. The default batch size is ten, which lets a citizen submit several reports or votes before needing to re-authenticate.

For each ticket, a \ac{UUID} is generated and hashed with ethers.id. The resulting 32-byte ticket ID is signed by the configured government wallet. The signed ticket and its issue record are stored by the simulator, and a previously assigned citizen seed is also returned. Because tickets consumed downstream solely as opaque signed nullifiers, the relayer and contracts remain independent of how a ticket was issued. Therefore, the identity layer can be strengthened over time without altering how the rest of the system verifies and consumes a ticket.

The \ac{DApp} derives a citizen private key by hashing the citizen seed together with a configured wallet salt, and an Ethereum wallet is created from the result. This process gives the same wallet for the same seed and salt, which lets a citizen return to the same pseudonymous identity across sessions without the system having to store a private key anywhere.

\subsection{Reporting Contract}
\label{subsec:reporting-contract}

The Reporting contract stores standard civic reports. Each report includes an ID, IPFS CID, report hash, submission nullifier, citizen pseudonym, relayer address, status, timestamps, phase deadline, assigned authority, vote counters, latest authority comment, and latest authority media evidence CID. A separate append-only mapping stores the full authority action history, which keeps a permanent audit trail of every action even though the main report record only needs to expose the latest one. The following eight statuses are implemented:

\begin{quote}
    \begin{enumerate}
        \item {PendingValidation}
        \item {CommunityRejected}
        \item {Open}
        \item {InProgress}
        \item {PendingRejectionReview}
        \item {PendingVerification}
        \item {Closed}
        \item {Reopened}
    \end{enumerate}

\end{quote}

Standard submissions are created as PendingValidation. The default voting window is six hours. Four voting methods are available namely simple majority, two-thirds supermajority, minimum threshold, and a hybrid of two methods. The simple-majority method is selected by default because it keeps everyday validation responsive. The other methods remain available through governance for deployments that need stronger confidence before a decision.

Mappings are maintained for used submission nullifiers and for used vote nullifiers in validation, verification, and rejection-review phases. Citizen pseudonym mappings also prevent one pseudonym from voting twice in the same phase, which is necessary because a determined citizen could acquire more than one ticket and attempt to vote twice. Checking the pseudonym closes this gap even though the ticket nullifier alone would not. Validation revotes are limited to quorum-failure cases and are capped at three cycles, so a report that fails to attract enough participation can be given another chance without allowing indefinite repeated attempts.

Authorized relayers submit reports and votes, and authorized authorities start work, add updates, mark reports as solved, and reject reports. Status checks are made before each change so that a transaction can only move a report through the transitions defined in Section~\ref{sec:report-lifecycle}. OpenZeppelin's ownership and reentrancy-guard modifiers are applied to protect the functions that change contract state.

\subsection{EmergencyReporting Contract}
\label{subsec:emergency-contract}

The EmergencyReporting contract stores urgent reports separately. This keeps the logic focused on the fast-track workflow rather than sharing the Reporting contract's community-validation mechanism. A valid emergency submission is created directly as Open, community validation is not performed first. The four emergency statuses are Open, InProgress, Resolved, and Reclassified.

An emergency can be resolved from Open or InProgress, since an emergency may already be resolved by the time an authority formally starts work on it. A false emergency can be reclassified. When reclassification is recorded, the citizen pseudonym is blocked from new emergency submissions for 30 days, which is implemented by computing the unlock time according to Eq.(~\ref{eq:emergency-penalty}).

\begin{equation}
    T_{\mathrm{unlock}} = T_{\mathrm{block}} + ( 30 \times 24 \times 60 \times 60)
    \label{eq:emergency-penalty}
\end{equation}

where \(T_{\mathrm{unlock}}\) is the unlock time and \(T_{\mathrm{block}}\) is the current block timestamp in seconds. Computing the unlock time from the block timestamp, rather than from an off-chain clock keeps the penalty period verifiable directly from on-chain data.

\subsection{AuthorityMultiSig Contract}
\label{subsec:multisig-contract}

The AuthorityMultiSig contract manages Super Admins, authority workers, profiles, and voting configuration. A proposal is created for adding or removing a Super Admin, adding or removing an authority worker, or changing the standard-report voting method. Instead of requiring a second confirmation step, the proposer automatically gives the first approval. Therefore no need for seperate step to confirm the proposal.

Whenever a vote is cast, the contract recomputes how many yes votes are needed using Eq.(~\ref{eq:governance-quorum}) and the live Super Admin count. Execution starts as soon as that threshold is met. Worker grants and revocations are pushed to the Reporting contract and, if the address is set, to EmergencyReporting as well. So permissions do not diverge between standard and emergency flows. At deploy time, ownership of the Reporting contract is transferred to the multisig, meaning protected settings can only be changed through an approved proposal rather than by one private key acting alone.

\subsection{OpinionPolling Contract}
\label{subsec:polling-contract}

Each poll record on the OpinionPolling contract holds an ID, the creating address, an \ac{IPFS} metadata \ac{CID}, a deadline, a type flag, and a boolean to indicate whether the poll is open or not. Both yes/no and multi-option formats are supported. Only wallets already recognised as authorities in the Reporting contract may open a new poll, so the same worker list governs reporting and consultation without duplicating access control.

Votes increment a counter keyed by poll ID and option index. A second mapping marks whether a given nullifier has already been spent on that poll, which blocks duplicate votes while leaving the tally easy to reconstruct from emitted events.


\section{Relayer Cryptography and Queue Processing}
\label{sec:relayer-queue-implementation}

Citizen reports and votes are submitted to the chain through a NestJS relayer backed by ethers.js. Before a report job is enqueued, the service runs three verification steps in the order shown in Figure~\ref{fig:relayer-pipeline-implementation}, starting with the lightest checks and ending with the heaviest.

\begin{enumerate}
    \item Recover the government signature embedded in the ticket ID and confirm it matches the configured government signer address.
    \item Hash every uploaded image with Keccak-256 and compare the result with the hash the \ac{DApp} supplied for that file.
    \item Rebuild the composite report hash using Eq.(~\ref{eq:report-hash}), recover the citizen signer from the payload signature, and confirm it matches the wallet address sent with the request.
\end{enumerate}

After these checks, the citizen pseudonym is derived according to Eq.(~\ref{eq:pseudonym}). Image buffers are converted to base64 before queue storage so that they can pass through Redis, which stores queue payloads as text-safe data.

\begin{figure}[!htb]
    \centering
    \includegraphics[width=0.95\textwidth,height=0.85\textheight,keepaspectratio]{Images/Chapter 4/relayer-pipeline-implementation.png}
    \caption{Relayer verification checks and BullMQ job pipeline implementation}
    \label{fig:relayer-pipeline-implementation}
\end{figure}

A BullMQ flow contains three ordered child jobs. The AI moderation job is run first, the IPFS upload job is run second, and the blockchain submission job is run third. The AI step has one attempt because a moderation rejection is a decision about the content itself. Retrying with the same input would not change that decision. The IPFS and blockchain steps allow three attempts each, because failures at those steps are more often transient network or RPC issues that a retry attempt can resolve. A failed child is configured to fail its parent flow, so a report can never be left in a silently inconsistent state, such as being moderated and stored but never anchored on-chain.

The HTTP response contains a job ID without waiting for all three steps. So the citizen's browser is never blocked for as long as the slowest step takes. Progress objects are emitted inside the relayer and are sent through an SSE endpoint. Each SSE stream is filtered by the citizen wallet address so a citizen only observes their own submissions. A separate vote queue is used for citizen vote transactions, keeping report processing and vote processing independent of each other's load.

\section{AI Moderation Implementation}
\label{sec:ai-implementation}

The AI component is implemented as one decision aggregator and three classifier services as safety, spam, and civic relevance. Splitting moderation into independent classifier services, coordinated by a single aggregator ensures each classifier can be developed, updated, and restarted on its own without affecting the others or requiring changes to the relayer.

\subsection{Request Protection and Aggregation}
\label{subsec:ai-aggregation}

Each moderation call from the relayer carries an \ac{API} key, a relayer signature, a timestamp, and a fresh nonce, as illustrated in Figure~\ref{fig:ai-request-protection}. The signature proves the payload came from our relayer, so stealing the key is not enough to forge traffic. The timestamp caps how long an intercepted request stays valid. The nonce table rejects any copy of a request that has already been seen inside that window.

\begin{figure}[!htb]
    \centering
    \includegraphics[width=0.95\textwidth,keepaspectratio]{Images/Chapter 4/ai-request-protection.png}
    \caption{AI moderation request protection and aggregation sequence}
    \label{fig:ai-request-protection}
\end{figure}

On receipt, the aggregator recovers the signer and checks it against the trusted relayer address. It rejects requests older than a configurable limit while recording each nonce in a local SQLite table so the same value cannot be presented twice. A full database server was not needed for that task. A lightweight file-backed store is enough for one service instance.

The aggregator then queries every classifier in turn. If a service is down or returns an error, the outcome is treated as a rejection, matching the policy described in Chapter~\ref{ch:architecture}. A fail on safety, civic relevance, spam, or any other critical rule ends the pipeline immediately. When no critical rule fires, the report is accepted only if at least two classifiers vote accept and none vote reject, so one misbehaving model cannot approve content on its own. The response bundles content hashes and may include an aggregator signature, giving the relayer a signed record of what was decided.

\subsection{Safety Service}
\label{subsec:safety-service}

Text safety is checked with unitary/toxic-bert. The first 512 characters are passed to the model pipeline, which comfortably covers a civic report description while keeping inference fast. The thresholds of implemented unsafe classifier are shown in Table~\ref{tab:safety-thresholds}.

\begin{table}[!htbp]
    \centering
    \caption{Implemented Toxic-BERT thresholds}
    \label{tab:safety-thresholds}
    \small
    \begin{tabular}{l|c|l}
        
        Label & Threshold & Critical \\
        \hline
        toxic & 0.50 & No \\
        \hline
        severe\_toxic& 0.50 & Yes \\
        \hline
        obscene & 0.60 & No \\
        \hline
        threat & 0.40 & Yes \\
        \hline
        insult& 0.60 & No \\
        \hline
        identity\_hate & 0.40 & Yes \\
        
    \end{tabular}
\end{table}

Labels linked to real-world harm, namely severe\_toxic, threat, and identity\_hate, are marked critical and trigger an immediate rejection on their own, while the remaining labels contribute to the aggregator's ordinary majority-vote decision alongside the other classifiers. This distinction means the more serious categories cannot be out-voted by an otherwise favourable spam or civic-relevance result.

Image safety is checked with Falconsai/nsfw\_image\_detection. The maximum score is used for the labels such as nsfw, and an image is rejected when this score is at least 0.70.

Accepted images are processed for faces with OpenCV Haar cascades. Frontal, alternative frontal, left-profile, and mirrored right-profile checks are used so that faces are detected from several common angles rather than only straight-on. Overlapping boxes are reduced, and Gaussian blur is applied to detected face areas, which protects the identity of bystanders who happen to appear in a citizen's photograph. The processed images are returned to the relayer for IPFS storage.

\subsection{Spam Service}
\label{subsec:spam-service}

Spam is checked with mrm8488/bert-tiny-finetuned-sms-spam-detection and a rule score. Combining a trained model with explicit rules is intentional. The model recognises spam patterns it was trained on. While the rules catch obvious cases such as bare URLs or excessive repeated characters, that a small model may not reliably learn on its own. The default thresholds are 0.85 for a strong model rejection, 0.65 for model support, 0.60 for a rule-only rejection, and 0.25 for rule support.

Rules add scores for very short text, known spam phrases, promotional words, URLs, repeated characters, and excessive symbols. The final rule score is capped at 1.0. A report is rejected when the model is strongly confident, when the rule score reaches the rejection threshold, or when both supporting thresholds are reached. Therefore, a moderately suspicious signal from both the model and the rules together is still enough to reject a report even when either signal alone would not reject it.

\subsection{Civic Relevance Service}
\label{subsec:civic-service}

Text relevance is checked with sentence-transformers/all-MiniLM-L6-v2. Normalized text embeddings are compared with precomputed reference embeddings by cosine similarity. The reference set covers common local issues alongside a general civic category so that a report does not need to match a narrow predefined topic exactly.

The default text relevance threshold is 0.38, and a lower maximum similarity causes rejection. This threshold is kept low deliberately so it only screens out content that is clearly unrelated to civic issues, rather than second-guessing a citizen's choice of words. The selected-category match threshold is 0.40, and a category mismatch produces an explanation but does not reject text that is otherwise civic. A mismatched category label alone will not stop someone from filing a report if the description itself is still on-topic.

\section{IPFS Implementation}
\label{sec:ipfs-implementation}

The IPFS layer contains an IPFS node and an Express HTTP service. To submit a complaint, description, category, and location are required. Up to five images are accepted by the storage endpoint, and each image entry contains its original name, MIME type, byte size, and base64 data.

One JSON envelope is formed with the following fields:

\begin{enumerate}
    \item type
    \item description
    \item category
    \item location
    \item imageCount
    \item images
    \item storedAt
\end{enumerate}

The complete envelope is added and pinned as one IPFS object with \ac{CID} version 1. A single \ac{CID} covers both metadata and images and can be used to verify the whole submission at once rather than checking each field separately. If blurred images are returned by the safety service, they replace the original buffers before this envelope is uploaded. Therefore, the privacy-preserved, face-blurred image gets the permanent \ac{CID}, rather than the original image.

The IPFS HTTP service is deployed on an internal service network reachable only from the relayer and other trusted backend services, with CORS and standard HTTP security headers applied at the edge of that network.

\section{Web Client Implementation}
\label{sec:web-client-implementation}

The public-facing client is a Next.js application built with React, Tailwind CSS, and ethers.js. Citizens log in through the identity simulator, file standard or emergency reports, watch reporting or voting progress, browse open cases, cast votes, and review their own submissions under a pseudonym. Authority accounts get a separate workflow for picking up assigned reports, posting progress notes, submitting resolution evidence, and running multisig governance and opinion polls.

Direct blockchain reads are made through a JSON-RPC provider. Citizen POST requests are sent to the relayer so that citizens do not need gas or direct wallet transaction handling. Authority and Super Admin actions are signed through MetaMask, because authority and governance actions are comparatively infrequent and their operators are already expected to hold a funded wallet.

The citizen wallet is derived from the citizen seed, and session data can optionally be protected by a user PIN. The browser uses \ac{PBKDF} with SHA-256 and 600,000 iterations to derive a 256-bit key, following widely recommended minimum iteration counts for password-based key derivation, and \ac{AES}-\ac{GCM} is used for encryption because it detects tampering as well as providing confidentiality. Each encryption also writes out a fresh 16-byte salt and 12-byte IV alongside the ciphertext, which means encrypting the same PIN twice yields different stored bytes.

The government identity simulator runs in its own React application. That split reflects a different trust boundary. The simulator handles credentials the public site should never see, and React is enough for the narrow login-and-ticket screen it provides.

\section{Deployment and Configuration}
\label{sec:deployment-configuration}

Every service runs in Docker and reads its settings from environment variables, so the same images can move from a laptop to a staging host by swapping a \texttt{.env} file rather than rebuilding code. Blockchain settings cover RPC endpoints, deployed contract addresses, chain ID, and relayer signing keys. The relayer layer adds the government signer address, pseudonym salt, Redis URL, AI aggregator URL, API key, and \ac{IPFS} base URL. The AI stack separately exposes trusted relayer credentials, per-model enable flags, classifier thresholds, maximum request age, the SQLite nonce path, and URLs for the safety, spam, and civic worker containers.

The prototype is deployed across two hosts, as shown in Figure~\ref{fig:deployment-topology}. The Geth nodes, relayer, Redis, identity simulator, and web application are grouped on one host, while the AI aggregator, its three classifier services, and the IPFS service are grouped on a second host. This split is deliberate. AI inference and image processing are comparatively heavy and can have variable latency. Keeping them on a separate host ensures a spike in moderation load will not compete for CPU or memory with the relayer or, more importantly with the Geth nodes that need to seal blocks on schedule.

\begin{figure}[!htb]
    \centering
    \includegraphics[width=0.9\textwidth,keepaspectratio]{Images/Chapter 4/deployment-topology.png}
    \caption{Deployment topology of the containerized services}
    \label{fig:deployment-topology}
\end{figure}

The AI workers communicate with the aggregator through an internal service network, and the IPFS HTTP endpoint is likewise reached only through that internal network.

Secrets such as private keys, API keys, Redis passwords, government signing keys, and PIN-derived session keys are kept in environment configuration. Separate values are used for development and deployment so that a development credential can never be mistaken for a production one.

\section{Summary}
\label{sec:implementation-summary}

This chapter has described how the design from Chapter~\ref{ch:architecture} was implemented.The implementation consists of a private Geth \ac{PoA} network with a dedicated RPC node, four smart contracts with clearly separated responsibilities, an identity simulator that issues signed single-use tickets, a relayer that verifies requests before queuing them through an ordered BullMQ pipeline, a fail-closed AI moderation ensemble, a single-CID IPFS envelope for complaint content, and Next.js and Vite web clients. The pieces described here, split contracts, isolated validator and RPC nodes, signed AI requests, queue retries, and gasless relaying, each map back to a decision in Chapter~\ref{ch:architecture}. Chapter~\ref{ch:testing} checks whether the built prototype actually meets those targets.
