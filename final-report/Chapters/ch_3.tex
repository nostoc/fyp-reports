\chapter{System Architecture and Workflow Design}
\label{ch:architecture}

This chapter details the system architecture and operational workflows of the proposed blockchain-based, community-assisted, privacy-preserving local governance reporting platform. To achieve citizen anonymity, data immutability, spam prevention, transparent civic accountability, and decentralized governance, a six-layer hybrid architecture is established. The separation of responsibilities between on-chain and off-chain environments is defined, inter-layer communication protocols are specified, mathematical state machine models are formulated, and deterministic workflows for citizen authentication, report submission, peer validation, authority resolution, public opinion polling, and multi-signature governance are outlined.

\section{Overall System Architecture}
\label{sec:overall-architecture}

A hybrid on-chain and off-chain architectural model is adopted to reconcile the immutability and transparency of distributed ledgers with the computational and storage constraints of smart contracts. High-volume media storage and complex machine learning inference are executed off-chain, while state transitions, access control, and cryptographic verification are enforced on-chain.

\subsection{Hybrid On-Chain/Off-Chain Execution Model}
\label{subsec:hybrid-model}

The platform partitions operations into two synchronized environments.
\begin{enumerate}
    \item \textbf{On-Chain Execution Environment:} Executed on a private, permissioned \ac{PoA} network. It maintains minimal, immutable state variables, including report metadata, opinion polling metadata, lifecycle state transitions, cryptographic content hashes, single-use ticket nullifiers,\ac{RBAC} configurations, multi-signature governance proposals, and community voting tallies.
    \item \textbf{Off-Chain Execution Environment:} Comprises data-intensive and computationally heavy microservices, including multimedia storage on \ac{IPFS}, automated multi-classifier AI content moderation, gasless transaction orchestration via a NestJS middleware relayer, automated wallet funding, and scheduled background cron jobs for voting window finalization.
\end{enumerate}

\subsection{Six-Layer Architectural Topology}
\label{subsec:six-layer-topology}

To achieve modularity, fault isolation, and maintainability, the system is organized into a six-layer topology as shown in the diagram 

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.95\textwidth,height=0.75\textheight,keepaspectratio]{Images/Chapter 3/layered-architecture.png}
    \caption{Six-layer architectural topology}
    \label{fig:layered-architecture}
\end{figure}

\begin{enumerate}
    \item User Layer: Represents the primary actors: citizens who report issues and cast validation votes, municipal authority workers who remediate reported infrastructure problems, and Super Admins who oversee system governance.
    \item Presentation (DApp) Layer: A responsive web application built with Next.js 14, React, and Tailwind CSS. Cryptographic key management and payload signing are handled on the client side using \texttt{ethers.js}. The DApp abstracts blockchain interactions so that citizens do not manage cryptocurrency wallets or native gas tokens.
    \item Identity Layer: Verifies citizen eligibility while preserving anonymity through a \ac{ZKP} GovID Simulator. Citizens authenticate against a municipal registry and receive batches of single-use government-signed ticket identifiers (\texttt{zkpTicketId}) alongside a unique citizen seed.
    \item Orchestration (Relayer) Layer: Serves as the gateway between the client DApp and the blockchain. Built with NestJS and Redis, the relayer executes dual-layer signature verification, manages asynchronous BullMQ job queues, provides \ac{SSE} for progress streaming, funds authority wallets via \texttt{AuthorityFundingService}, and runs daily cron jobs via \texttt{CronService}.
    \item Off-Chain Services Layer: Consists of specialized services for media storage and automated content moderation.
    \begin{enumerate}
        \item \ac{AI} Content Moderation Service Ensemble: A microservice network comprising a Safety Classifier, Spam Classifier, Civic Relevance Classifier, and Moderation Decision Aggregator.
        \item \ac{IPFS}  Distributed Storage: A peer-to-peer storage cluster managed via a NestJS HTTP service abstraction that pins report descriptions, photographic evidence, and resolution media.
    \end{enumerate}
    \item Blockchain Layer: A private permissioned ledger running the Clique \ac{PoA} consensus engine. It executes compiled Solidity smart contracts (Reporting.sol, EmergencyReporting.sol, OpinionPolling.sol, and AuthorityMultiSig.sol) to enforce lifecycle rules, access registries, nullifier sets, and an append-only audit log.
\end{enumerate}

\section{Subsystem Interconnection and Interaction Design}
\label{sec:subsystem-interconnection}

Robust, cryptographically verifiable protocols are established to link the six architectural layers.

\subsection{Communication Protocols and Interface Specifications}
\label{subsec:comm-protocols}

Inter-subsystem communication is governed by three primary interfaces:
\begin{enumerate}
    \item \ac{REST}/\ac{HTTPS} \ac{API}s: Used for communication between the DApp, \ac{ZKP} GovID Simulator, and Backend Relayer. Endpoints enforce transport-layer security (TLS 1.3), rate limiting, and request schema validation.
    \item \ac{JSON}-\ac{RPC}  Protocols: Used by the relayer and off-chain services to interact with the PoA blockchain nodes. 
    \item \ac{IPFS} \ac{RPC} \ac{API} and Gateway: The relayer communicates with the IPFS daemon via \ac{RPC} \ac{API} on port 5001 for pinning operations. Media rendering on the client DApp uses the IPFS HTTP gateway on port 8080.
\end{enumerate}

\subsection{Dual-Layer Cryptographic Verification Engine}
\label{subsec:dual-layer-verification}

To enable gasless citizen submissions without compromising security or payload integrity, a dual-layer cryptographic verification engine is implemented in the relayer. Two independent \ac{ECDSA} signatures are validated prior to queue dispatch.

\begin{enumerate}
    \item Government Ticket Signature Verification: The single-use ticket (\texttt{zkpTicketId}) signature is verified against the government authority public key to confirm that the submitter is an authenticated citizen.
    \item Citizen Composite Payload Signature Verification: The citizen's ephemeral private key signs the composite report hash computed as shown in the Eq. \ref{eq:citizen-comp-payload}.
     \begin{equation}
        \mathcal{H}_{\text{report}} = \text{keccak256}\Big(\text{description} \parallel \text{zkpTicketId} \parallel \mathcal{H}_{\text{media}}\Big)
    \label{eq:citizen-comp-payload}
    \end{equation}
    
    where $\mathcal{H}_{\text{report}}$ is the composite report hash committed to by the citizen, $\text{description}$ is the plaintext civic issue description, $\text{zkpTicketId}$ is the single-use government-signed identity ticket, $\mathcal{H}_{\text{media}}$ is the cryptographic hash of all attached media files, and $\parallel$ denotes byte-level concatenation. The relayer recovers the signer address from the submitted signature and compares it against the citizen's ephemeral public key to verify that the payload has not been modified in transit. This is based on the ECDSA signature recovery scheme as used in the Ethereum protocol~\cite{buterin_ethereum_2014}.
\end{enumerate}

\subsection{AI Content Moderation Service Ensemble Interconnection}
\label{subsec:ai-moderation-interconnection}

Automated content moderation is performed by four containerized microservices operating on an isolated Docker network. 
\begin{enumerate}
    \item Safety Classifier Service: Evaluates text for toxicity using \texttt{unitary/toxic-bert} and images for adult content using \texttt{Falconsai/nsfw\_image\_detection}. Safe images with human faces are processed through an OpenCV Haar cascade blurring pipeline.
    \item Spam and Abuse Classifier Service: Detects commercial spam, repeated character patterns, and excessive symbols using \texttt{mrm8488/bert-tiny-finetuned-sms-spam-detection} and a rule-based engine.
    \item Civic Relevance Classifier Service: Computes 384-dimensional sentence embeddings using \texttt{sentence-transformers/all-MiniLM-L6-v2} and evaluates cosine similarity against nine civic reference categories.
    \item Moderation Decision Aggregator: Acts as the single entry point. It verifies relayer signatures, checks nonces, enforces immediate rejection on safety or non-civic violations, and applies majority consensus across worker votes.
\end{enumerate}

\subsection{Two-Tier Multi-Signature Governance Topology}
\label{subsec:multisig-governance}

Administrative access is governed by \texttt{AuthorityMultiSig.sol}, which holds ownership of \texttt{Reporting.sol}. Stakeholders are categorized as given below. 
\begin{enumerate}
    \item Super Admins: Senior municipal officials who propose and authorize officials.  The required voting quorum is calculated dynamically as given in \ref{eq:super-admin-quorum}.
    \begin{equation}
        \text{Quorum} = \Big\lfloor \frac{\texttt{superAdminCount}}{2} \Big\rfloor + 1
    \label{eq:super-admin-quorum}
    \end{equation}
    where $\text{Quorum}$ is the minimum number of Super Admin approval votes required to execute a governance proposal, $\texttt{superAdminCount}$ is the current total number of registered Super Admins on-chain, and $\lfloor \cdot \rfloor$ denotes the floor function. The formula ensures that a strict majority (more than half) of all Super Admins must approve every governance action, which is consistent with standard multi-party threshold signature schemes~\cite{cryptoeprint:2016/013}.
    \item Authority Workers: Field officers authorized to claim, update, solve, or reject reports. Access permissions are granted or revoked exclusively through multi-sig proposals. 
    \item On-Chain Profile Directory: Stores immutable profile structs (\texttt{name}, \texttt{position}, \texttt{department}) for all municipal personnel.
\end{enumerate}

\subsection{Automated Relayer Funding and Cron Orchestration}
\label{subsec:relayer-funding-cron}

To automate background administrative tasks, the relayer incorporates two background services:
\begin{enumerate}
    \item Authority Funding Service: Listens for \texttt{ProposalExecuted} events. When a proposal to add an authority executes, the service automatically transfers 5.0 ETH from the relayer treasury to the new authority's wallet.
    \item Background Cron Service: Executes daily balance monitoring at 01:00 which tops up wallets below 1.0 ETH and daily voting window finalization at 00:00 for expired reports.
\end{enumerate}

\subsection{Asynchronous Job Queue Architecture}
\label{subsec:async-queue}

Report processing is decoupled from HTTP requests using a Redis-backed BullMQ job queue. Submissions are enqueued as parent **Flow Jobs** containing three sequential child steps:
\begin{enumerate}
    \item Step 1 - AI Moderation: Executes content classification.
    \item Step 2 - IPFS Upload: Reads Step 1 results and pins text and blurred images to IPFS.
    \item Step 3 - Blockchain Submission: Submits \texttt{submitReport()} to the smart contract.
\end{enumerate}

Transient errors trigger an exponential backoff retry policy according to Eq. \ref{eq:bullmq-error}.
\begin{equation}
    \Delta t_{\text{retry}}(k) = t_{\text{base}} \times 4^{k-1}, \quad k \in \{1, 2, 3\}, \quad t_{\text{base}} = 2{,}000\,\text{ms}
\label{eq:bullmq-error}
\end{equation}
where $\Delta t_{\text{retry}}(k)$ is the delay applied before the $k$-th retry attempt, $t_{\text{base}} = 2{,}000$\,ms is the base delay for the first retry, and $k$ is the retry attempt index ranging from 1 to 3. The multiplier $4^{k-1}$ produces delays of 2\,s, 8\,s, and 32\,s for the first, second, and third attempts respectively. This exponential growth reduces contention on transient remote services such as IPFS and blockchain RPC nodes~\cite{karn1987improving}.

\subsection{Real-Time Status Notification via \ac{SSE}}
\label{subsec:sse-gateway}

Progress updates are streamed to the client DApp over a persistent \ac{SSE} connection. Queue workers emit progress events through NestJS \texttt{EventEmitter2}, which are pushed into an RxJS \texttt{Subject} stream in \texttt{ReportStatusGateway}. Updates are filtered by citizen public key so that users receive only their own job progress events.

\label{subsec:validator-topology}

\begin{itemize}

    \item Regional Oversight Validator Node: Operated by a regional supervisory body.
    \item Independent NGO Validator Node: Managed by a recognized civil society organization to prevent unilateral censorship.

\section{Detailed Workflow and Finite State Machine (FSM) Design}
\label{sec:detailed-workflow-fsm}

The platform operational logic is formalized as a deterministic Finite State Machine (\ac{FSM}).

\subsection{Finite State Machine (FSM) Formal Definition}
\label{subsec:fsm-overview}

A civic issue report lifecycle is defined as an eight-state FSM:
\begin{equation}
    \mathcal{S} = \big\{ S_0, S_1, S_2, S_3, S_4, S_5, S_6, S_7 \big\}
\end{equation}
where $\mathcal{S}$ is the set of all valid report lifecycle states, and each $S_i$ represents a distinct, immutable on-chain status. 

Specifically:
\begin{enumerate}
    \item $S_0 = \text{PendingValidation}$ (submitted and awaiting community vote)
    \item $S_1 = \text{CommunityRejected}$ (terminal rejection by community consensus)
    \item $S_2 = \text{Open}$ (validated and awaiting authority action)
    \item $S_3 = \text{InProgress}$ (claimed by an authority worker)
    \item $S_4 = \text{PendingRejectionReview}$ (authority-issued rejection under community appeal)
    \item $S_5 = \text{PendingVerification}$ (resolution submitted and awaiting community verification)
    \item $S_6 = \text{Closed}$ (terminal resolved state)
    \item $S_7 = \text{Reopened}$ (resolution rejected; returned to authority)
\end{enumerate}

No state outside $\mathcal{S}$ is representable in the contract storage. State transitions are governed by configurable time windows, access roles, and four persistent nullifier mappings to prevent double voting.

\subsection{Anonymous Public Opinion Polling Workflow}
\label{subsec:opinion-polling-workflow}

Figure~\ref{fig:opinion-polling-workflow} details the public opinion polling workflow managed by \texttt{OpinionPolling.sol}. This workflow allows authorized municipal officials to gather anonymous community feedback on public proposals (such as zoning changes or municipal budgets).

The polling workflow proceeds as follows:
\begin{enumerate}
    \item \textbf{Poll Creation:} An authorized official calls \texttt{createOfficialPoll(ipfsCid, deadline, pollType)}. The contract verifies official permissions against \texttt{Reporting.sol}, stores proposal metadata CID, and assigns a unique \texttt{pollId}.
    \item \textbf{DApp Poll Display:} The DApp fetches poll documentation from IPFS and renders voting choices (\texttt{TrueFalse} or \texttt{MultiChoice}) to citizens.
    \item \textbf{Anonymous Vote Submission:} Citizens cast votes anonymously using single-use ticket nullifiers. The relayer submits \texttt{castVote(pollId, optionIndex, nullifier)}.
    % \item \textbf{Nullifier Check & Tallying:} The contract verifies \texttt{!nullifierVoted[pollId][nullifier]}, marks the nullifier used, and increments the option tally \texttt{pollResults[pollId][optionIndex]}.
    \item \textbf{Poll Finalization:} Upon reaching the deadline, \texttt{finalizePoll(pollId)} freezes results, producing an immutable public consultation record.
\end{enumerate}

\section{Summary and Expected Outcomes}
\label{sec:summary-outcomes}

This chapter presented the theoretical framework, six-layer topology, cryptographic verification schemes, two-tier governance structures, state machine definitions, and operational workflows of the platform. Through the integration of ZKP authentication, AI moderation, IPFS off-chain storage, and PoA smart contract execution, the platform achieves anonymous citizen participation, automated spam suppression, and tamper-evident municipal accountability.
