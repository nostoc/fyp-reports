\chapter{System Architecture and Workflow Design}
\label{ch:architecture}

This chapter presents the comprehensive architectural framework and operational workflow design of the proposed blockchain-based, community-assisted, privacy-preserving reporting platform for local governance. Achieving an optimal balance between citizen anonymity, data immutability, spam mitigation, transparent civic accountability, and decentralized administrative governance requires a structured, multi-layered system architecture. This chapter details the division of responsibilities across on-chain and off-chain components, specifies the communication and verification protocols between architectural layers, defines the underlying mathematical and finite state machine (\ac{FSM}) models governing issue lifecycles, and outlines the deterministic workflows executed during citizen authentication, report submission, community validation, authority resolution, public opinion polling, and two-tier multi-signature governance.

\section{Overall System Architecture}
\label{sec:overall-architecture}

The proposed system adopts a hybrid on-chain and off-chain architectural design. While decentralized ledger technology provides immutability, transparency, and tamper-evident audit trails, executing high-capacity media storage and computationally complex algorithms directly on-chain is technically unfeasible and economically prohibitive. Consequently, the architecture strictly decouples immutable state management and cryptographic verification from data storage and content evaluation.

\subsection{Hybrid On-Chain/Off-Chain Model}
\label{subsec:hybrid-model}

The hybrid model separates system operations into two synchronized environments:
\begin{enumerate}
    \item \textbf{On-Chain Execution Environment:} Implemented as a private, permissioned \ac{PoA} blockchain network. This environment stores minimal, immutable state information, including report metadata, lifecycle state transitions, cryptographic hashes of report payloads, one-time ticket nullifiers, role-based access control (\ac{RBAC}) permissions, two-tier multi-signature governance proposals, on-chain official identity profiles, and community voting tallies.
    \item \textbf{Off-Chain Execution Environment:} Encompasses computationally intensive and data-heavy operations that cannot occur on-chain. This includes the storage of high-resolution multimedia evidence in \ac{IPFS}, automated natural language and visual content moderation via an ensemble of \ac{AI} classifiers, gasless transaction orchestration performed by a middleware backend relayer, automated account funding via event listeners, and background cron jobs for voting window batch finalizations.
\end{enumerate}

\subsection{Six-Layer Architectural Topology}
\label{subsec:six-layer-topology}

To achieve modularity, fault isolation, and scalability, the overall architecture is structured into a six-layer topology. Each layer encapsulates specific functional responsibilities and exposes standardized interfaces to adjacent layers:

\begin{enumerate}
    \item \textbf{User Layer:}
    This layer comprises the primary participants interacting with the ecosystem: civic citizens, municipal government authorities, and pre-approved institutional stakeholders such as \ac{NGO}s. Citizens report civic issues and participate in validation voting, while authorities monitor, claim, and resolve reported infrastructure problems under the governance of municipal Super Admins.

    \item \textbf{Presentation (DApp) Layer:}
    The presentation layer consists of a responsive, web-based \ac{DApp} built with Next.js and React. It serves as the primary interface for citizens, government officials, and municipal administrators. For citizens, the \ac{DApp} provides intuitive workflows for authentication, report submission, media uploading, community feed browsing, and anonymous voting. For authorities and Super Admins, it provides an authenticated dashboard to track open reports, claim tasks, post mid-work progress updates, mark issues as resolved, and submit or vote on two-tier multi-signature governance proposals. The presentation layer abstracts underlying blockchain complexity, allowing users to interact with the platform without installing cryptocurrency wallets or managing native gas assets.

    \item \textbf{Identity and Authentication Layer:}
    This layer is responsible for verifying citizen credentials and issuing cryptographic proof of entitlement without associating \ac{PII} with on-chain activities. Implemented via the Zero-Knowledge Proof (\ac{ZKP}) GovID Simulator, this layer authenticates citizens against an official municipal registry and generates batches of single-use, government-signed ticket identifiers (\texttt{zkpTicketId}) along with a unique citizen seed. This mechanism establishes a trust anchor that prevents Sybil attacks while ensuring complete identity decoupling.

    \item \textbf{Middleware Orchestration (Relayer) Layer:}
    The backend relayer acts as the centralized gateway and coordination bridge between web clients and the blockchain network. Built using NestJS, the relayer receives signed report payloads and meta-transactions from the \ac{DApp}, executes a dual-layer cryptographic verification of government-signed tickets and citizen signatures, forwards report text and media to the \ac{AI} moderation service, anchors accepted content to \ac{IPFS}, and submits gas-sponsored transactions to the blockchain on behalf of users. Additionally, this layer incorporates an automated \texttt{AuthorityFundingService} to fund newly approved municipal workers and a background \texttt{CronService} to execute automated batch finalization of expired voting phases.

    \item \textbf{Off-Chain Services Layer:}
    This layer hosts specialized services required for content validation and decentralized storage:
    \begin{itemize}
        \item \textit{AI Content Moderation Ensemble:} A multi-oracle machine learning service that evaluates textual descriptions and visual evidence for spam, toxicity, abuse, and civic relevance before blockchain submission.
        \item \textit{IPFS Distributed Storage:} A peer-to-peer storage network that retains raw report descriptions, images, and completion evidence, returning immutable \ac{CID}s that are subsequently recorded on-chain.
    \end{itemize}

    \item \textbf{Blockchain Ledger Layer:}
    The foundation of the architecture is a private, permissioned blockchain running under the Clique \ac{PoA} consensus engine. This layer executes the compiled smart contract suite—comprising \texttt{Reporting.sol}, \texttt{OpinionPolling.sol}, and \texttt{AuthorityMultiSig.sol}—which enforce deterministic lifecycle rules, manage two-tier municipal access control, maintain on-chain profile directories, track one-time ticket nullifiers, and record an append-only audit trail of all governance events.
\end{enumerate}

\section{Subsystem Interconnection \& Interaction Design}
\label{sec:subsystem-interconnection}

The operational integrity of the platform depends on robust, cryptographically secure communication protocols between the six architectural layers. This section details the interface specifications, verification mechanisms, decentralized governance topology, automated funding services, and interconnection topologies that bind the subsystems together.

\subsection{Communication Protocols and Interface Specifications}
\label{subsec:comm-protocols}

Inter-layer communication is governed by three primary protocol interfaces:
\begin{enumerate}
    \item \textbf{REST/HTTPS API Protocols:} The presentation \ac{DApp} communicates with the ZKP GovID Simulator and the Backend Relayer over secure HTTPS. Report submissions, ticket requests, and polling queries are structured as standard JSON payloads. REST endpoints enforce rate-limiting, request validation, and transport-layer encryption.
    \item \textbf{JSON-RPC and WebSocket Protocols:} The Backend Relayer and \ac{AI} Oracle workers communicate with the private PoA blockchain via Ethereum-compatible JSON-RPC and WebSocket connections over HTTP/WSS. WebSocket providers enable real-time event streaming, allowing off-chain workers to subscribe to contract events such as \texttt{ReportCreated}, \texttt{ReportStatusChanged}, and \texttt{ProposalExecuted} with sub-second latency.
    \item \textbf{IPFS HTTP Gateway and RPC API:} The Backend Relayer and \ac{AI} Oracles interact with the local \ac{IPFS} daemon via its RPC API (port 5001) for pinning files and retrieving metadata, while client-side media rendering utilizes decentralized HTTP gateways.
\end{enumerate}

\subsection{Dual-Layer Cryptographic Verification Engine}
\label{subsec:dual-layer-verification}

To prevent unauthorized submissions and payload tampering without requiring citizens to submit transactions directly to the blockchain, the Backend Relayer implements a dual-layer cryptographic verification engine. When a citizen submits a report, the relayer evaluates two distinct signatures before initiating off-chain storage or on-chain anchoring:

\begin{enumerate}
    \item \textbf{Government Ticket Authenticity Verification:} The relayer inspects the single-use ticket identifier (\texttt{zkpTicketId}) attached to the request. It verifies the cryptographic signature generated by the ZKP GovID Simulator using the official government authority's ECDSA public key. This confirms that the submitter is a verified citizen and that the ticket has not been forged.
    \item \textbf{Citizen Payload Integrity Verification:} The relayer verifies the citizen's ECDSA signature over the composite report hash, defined mathematically as:
    \begin{equation}
        \mathcal{H}_{\text{report}} = \text{keccak256}\Big(\text{description} \parallel \text{zkpTicketId} \parallel \mathcal{H}_{\text{media}}\Big)
    \end{equation}
    By verifying that the payload hash signed by the citizen's ephemeral private key matches the received data, the relayer ensures that neither man-in-the-middle attackers nor the relayer itself can alter the report description or media evidence.
\end{enumerate}

\subsection{AI Moderation Oracle Ensemble Interconnection}
\label{subsec:ai-oracle-interconnection}

Content moderation is executed through an interconnected ensemble of machine learning oracles designed to filter spam, malicious text, and non-civic media before immutable on-chain anchoring occurs. The ensemble is composed of three specialized oracle nodes coordinated by an Oracle Aggregator:

\begin{enumerate}
    \item \textbf{Safety Oracle Node:} Evaluates textual submissions for abusive, hateful, or threatening language using fine-tuned transformer models (\texttt{unitary/toxic-bert}), and inspects visual evidence for inappropriate or adult content using deep learning image classifiers.
    \item \textbf{Spam and Abuse Oracle Node:} Identifies unsolicited promotional messages, gibberish, and repetitive flood attacks using lightweight classification models (\texttt{bert-tiny-finetuned-sms-spam-detection}) combined with statistical heuristic filters.
    \item \textbf{Civic Relevance Oracle Node:} Generates semantic vector embeddings of report descriptions using \texttt{sentence-transformers/all-MiniLM-L6-v2} and computes cosine similarity scores against a domain-specific lexicon of municipal infrastructure categories (e.g., road hazards, sanitation, street lighting) to discard irrelevant submissions.
    \item \textbf{Oracle Aggregator Node:} Acts as the unified verification gateway. It collects signed moderation verdicts from each oracle worker, verifies request nonces and timestamps to prevent replay attacks, enforces an immediate rejection override if the Safety Oracle detects severe toxicity, and otherwise applies a majority-consensus rule to generate a definitive \texttt{ACCEPT} or \texttt{REJECT} decision.
\end{enumerate}

\subsection{Two-Tier Multi-Signature Governance \& Access Control Topology}
\label{subsec:multisig-governance}

To prevent centralized abuse of administrative privileges and ensure transparent municipal accountability, access control is managed through a two-tier multi-signature governance contract, \texttt{AuthorityMultiSig.sol}, to which ownership of \texttt{Reporting.sol} is transferred upon deployment. The governance architecture divides municipal stakeholders into two distinct hierarchies:

\begin{enumerate}
    \item \textbf{Super Admins:} A consortium of high-ranking municipal officials (e.g., Mayor, Deputy Mayor, Chief Executive Officer, and Town Planner) responsible for governing the ecosystem. Super Admins hold exclusive authority to submit and vote on governance proposals. Quorum is dynamically calculated as a majority of current Super Admins:
    \begin{equation}
        \text{Quorum} = \Big\lfloor \frac{\texttt{superAdminCount}}{2} \Big\rfloor + 1
    \end{equation}
    Once a proposal reaches quorum, it executes automatically.
    \item \textbf{Authority Workers:} Municipal engineering and maintenance staff authorized to act on civic issues in \texttt{Reporting.sol} (executing \texttt{startWork}, \texttt{addAuthorityUpdate}, \texttt{markAsSolved}, and \texttt{rejectIssue}). An Authority Worker's access can be granted or revoked exclusively through Super Admin multi-sig proposals (\texttt{AddAuthority} and \texttt{RemoveAuthority}).
    \item \textbf{On-Chain Profile Directory:} To establish institutional transparency, every Super Admin and Authority Worker has an immutable on-chain identity profile (\texttt{Profile} struct) storing their full name, official title, and municipal department. Citizens browsing the \ac{DApp} can inspect the profile of the assigned authority responsible for solving a civic report.
\end{enumerate}

When an \texttt{AddAuthority} or \texttt{RemoveAuthority} proposal achieves quorum, \texttt{AuthorityMultiSig.sol} performs a cross-contract invocation to \texttt{IReporting.setAuthority(target, authorized)}, instantly updating the access registry on the core reporting contract.

\subsection{Automated Relayer Funding \& Cron Orchestration Design}
\label{subsec:relayer-funding-cron}

To bridge on-chain access control with seamless off-chain operational readiness, the Backend Relayer incorporates two specialized automation services:

\begin{enumerate}
    \item \textbf{Authority Funding Service (\texttt{AuthorityFundingService}):}
    While \texttt{AuthorityMultiSig.sol} manages permissions, newly authorized municipal staff require native ETH to pay for transaction gas on the permissioned PoA blockchain. The relayer's funding service listens via WebSocket for \texttt{ProposalExecuted} events emitted by \texttt{AuthorityMultiSig.sol}. When an \texttt{AddAuthority} proposal executes, the service automatically transfers a configurable top-up balance (defaulting to 5.0 ETH) from the pre-funded relayer treasury to the new Authority Worker's wallet. This cleanly decouples on-chain governance logic from automated treasury administration.

    \item \textbf{Background Cron Orchestration (\texttt{CronService}):}
    The relayer executes two scheduled background orchestration workflows:
    \begin{itemize}
        \item \textit{Automated Balance Monitoring:} A daily scheduled cron job (\texttt{0 1 * * *}, Colombo timezone) scans the balances of all registered Super Admins and Authority Workers, automatically topping up any account whose balance drops below the minimum operational threshold (1.0 ETH).
        \item \textit{Voting Window Batch Finalization Engine:} While \texttt{Reporting.sol} supports lazy evaluation when a user submits a vote after a phase deadline, reports with zero subsequent voting activity could remain indefinitely pending. To prevent workflow stagnation, a daily midnight cron job scans the blockchain for reports in voting phases ($S_0 = \texttt{PendingValidation}$, $S_4 = \texttt{PendingRejectionReview}$, or $S_5 = \texttt{PendingVerification}$) where $\text{block.timestamp} > \texttt{phaseDeadline}$. For all expired reports found, the cron service executes a batch transaction calling \texttt{batchFinalizeVotingWindows}, forcing deterministic state transitions across the platform.
    \end{itemize}
\end{enumerate}

\subsection{Private Permissioned Validator Network Topology}
\label{subsec:validator-topology}

The underlying ledger operates as a private, permissioned Ethereum-compatible network utilizing the Clique \ac{PoA} consensus protocol. To ensure distributed governance without the energy consumption and latency of Proof-of-Work (\ac{PoW}), block sealing authority is restricted to a consortium of pre-approved institutional validator nodes. The consortium comprises three primary validator nodes:
\begin{itemize}
    \item \textbf{Municipal Authority Validator Node:} Hosted by local government administrative departments responsible for infrastructure maintenance.
    \item \textbf{Regional Oversight Validator Node:} Managed by regional or provincial supervisory bodies to ensure inter-agency auditing.
    \item \textbf{Independent Civic NGO Validator Node:} Operated by recognized civil society organizations to maintain democratic equilibrium and prevent unilateral censorship by government nodes.
\end{itemize}

\section{Detailed Workflow \& Finite State Machine (FSM) Design}
\label{sec:detailed-workflow-fsm}

The core operational logic of the platform is formalized as a mathematical Finite State Machine (\ac{FSM}) implemented within the \texttt{Reporting.sol} smart contract. This section details the state transitions, cryptographic nullifier protections, and deterministic workflows that govern a civic report from initial submission to post-resolution verification.

\subsection{Finite State Machine (FSM) Overview}
\label{subsec:fsm-overview}

A civic issue report is modeled as an eight-state deterministic \ac{FSM}. Let $\mathcal{S}$ define the discrete set of legal report states:
\begin{equation}
    \mathcal{S} = \big\{ S_0, S_1, S_2, S_3, S_4, S_5, S_6, S_7 \big\}
\end{equation}
where:
\begin{itemize}
    \item $S_0 = \texttt{PendingValidation}$: The initial state upon on-chain submission; the report is accessible on the community feed for peer validation voting within a 6-hour window.
    \item $S_1 = \texttt{CommunityRejected}$: A terminal state reached if community downvotes exceed upvotes during the validation phase.
    \item $S_2 = \texttt{Open}$: An active state entered when a report achieves community consensus; the issue becomes actionable for municipal authorities.
    \item $S_3 = \texttt{InProgress}$: An active state entered when an assigned authority claims the report and begins physical infrastructure repairs.
    \item $S_4 = \texttt{PendingRejectionReview}$: A review state entered if an authority rejects an issue as invalid; the community is granted a 6-hour window to uphold or appeal the rejection.
    \item $S_5 = \texttt{PendingVerification}$: A verification state entered after an authority marks an issue as solved; citizens physically inspect the repair and cast accept/reject votes within a 6-hour window.
    \item $S_6 = \texttt{Closed}$: A terminal state indicating that an issue has been successfully resolved and community-verified, or that an authority rejection was upheld.
    \item $S_7 = \texttt{Reopened}$: An active state triggered if the community rejects a claimed repair during verification or successfully appeals an authority rejection.
\end{itemize}

State transitions are strictly guarded by role-based access control (\ac{RBAC}), temporal window constraints ($\Delta t_{\text{window}} = 6\text{ hours}$), and cryptographic nullifier tracking. To prevent Sybil attacks and double-voting, the smart contract records used ticket hashes in persistent mappings (\texttt{usedSubmissionNullifiers}, \texttt{usedValidationVoteNullifiers}, \texttt{usedVerificationVoteNullifiers}, and \texttt{usedRejectionReviewVoteNullifiers}), enforcing the Checks-Effects-Interactions (CEI) design pattern.

\subsection{Citizen Authentication \& Identity Decoupling Workflow}
\label{subsec:auth-workflow}

The authentication workflow decouples a citizen's real-world civic identity from their on-chain actions, preventing transaction linkability while ensuring that only eligible citizens can participate. Figure~\ref{fig:authentication-workflow} illustrates the sequential steps of the authentication and credential issuance process.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.95\textwidth,height=0.75\textheight,keepaspectratio]{Images/Chapter 3/authentication_workflow.png}
    \caption{Citizen Authentication and Identity Decoupling Workflow}
    \label{fig:authentication-workflow}
\end{figure}

The authentication workflow proceeds through five deterministic steps:
\begin{enumerate}
    \item \textbf{Credential Submission:} The citizen inputs their official National Identity Number (NID) and password into the \ac{DApp} login interface.
    \item \textbf{Zero-Knowledge Verification:} The \ac{DApp} transmits an authentication request to the ZKP GovID Simulator. The simulator verifies the credentials against the mock government database without revealing or retaining sensitive identification attributes.
    \item \textbf{Ticket Batch Generation:} Upon successful verification, the simulator generates a batch of ten randomized, single-use ticket identifiers ($\texttt{zkpTicketId}_1, \dots, \texttt{zkpTicketId}_{10}$) along with a unique citizen seed.
    \item \textbf{Cryptographic Signing:} The simulator cryptographically signs each ticket identifier using the government authority's ECDSA private key, establishing proof of validity.
    \item \textbf{Local Browser Storage:} The signed ticket batch and citizen seed are returned to the client and stored securely within local browser storage. For on-chain tracking of personal submissions, the client derives a deterministic, unlinkable citizen pseudonym:
    \begin{equation}
        \text{Pseudonym} = \text{keccak256}\Big(\text{citizenPubKey} \parallel \text{DOMAIN\_SALT}\Big)
    \end{equation}
\end{enumerate}

\subsection{Report Submission \& Moderation Pipeline}
\label{subsec:submission-pipeline}

The report submission workflow coordinates client-side cryptographic signing, relayer verification, AI content moderation, off-chain IPFS storage, and on-chain transaction anchoring. Figure~\ref{fig:report-submission-workflow} depicts the complete report submission and moderation pipeline.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.95\textwidth,height=0.75\textheight,keepaspectratio]{Images/Chapter 3/report_submission_workflow.png}
    \caption{Report Submission, AI Moderation, and Blockchain Anchoring Pipeline}
    \label{fig:report-submission-workflow}
\end{figure}

The submission pipeline executes as follows:
\begin{enumerate}
    \item \textbf{Payload Structuring and Signing:} The citizen selects an issue category, inputs a textual description, and attaches optional media evidence. The \ac{DApp} computes the composite report hash ($\mathcal{H}_{\text{report}}$), signs it using the citizen's ephemeral private key, and selects an unused signed ticket from local storage.
    \item \textbf{Relayer Transmission:} The \ac{DApp} transmits the complete payload—comprising raw text, media files, government-signed ticket, and citizen signature—to the Backend Relayer via HTTPS POST.
    \item \textbf{Cryptographic Payload Verification:} The relayer verifies that the ticket signature corresponds to the government authority and that the citizen's signature matches the report hash. If verification fails, the request is rejected immediately.
    \item \textbf{AI Content Moderation:} The relayer forwards the text and media to the AI Moderation Ensemble. The Oracle Aggregator evaluates the submission against toxicity, spam, and civic relevance classifiers. If the ensemble returns a \texttt{REJECT} verdict, the relayer aborts the submission and returns a descriptive error to the \ac{DApp}.
    \item \textbf{IPFS Content Anchoring:} Upon receiving an \texttt{ACCEPT} verdict, the relayer uploads the report text and media files to \ac{IPFS}, obtaining the immutable Content Identifier (\texttt{ipfsCid}).
    \item \textbf{On-Chain Transaction Submission:} The relayer constructs a transaction calling \texttt{submitReport} on \texttt{Reporting.sol}, passing \texttt{ipfsCid}, $\mathcal{H}_{\text{report}}$, the single-use ticket hash as \texttt{submissionNullifier}, and the citizen's derived pseudonym. The relayer signs the transaction with its own wallet, sponsoring gas costs.
    \item \textbf{Smart Contract Nullifier Enforcement:} The smart contract checks \texttt{usedSubmissionNullifiers[submissionNullifier]}. If the nullifier was previously consumed, the transaction reverts. Otherwise, the contract marks the nullifier as used, initializes the report in state $S_0 (\texttt{PendingValidation})$, sets the phase deadline to $\text{block.timestamp} + 6\text{ hours}$, and emits the \texttt{ReportSubmitted} event.
\end{enumerate}

\subsection{Community Consensus \& Validation Workflow}
\label{subsec:validation-workflow}

To filter spam and ensure that only genuine civic concerns escalate to municipal authorities, newly submitted reports undergo community validation. Figure~\ref{fig:community-validation-workflow} illustrates the community consensus and peer-validation workflow.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.95\textwidth,height=0.75\textheight,keepaspectratio]{Images/Chapter 3/community_validation_workflow.png}
    \caption{Community Consensus and Peer-Validation Workflow}
    \label{fig:community-validation-workflow}

The validation workflow proceeds as follows:
\begin{enumerate}
    \item \textbf{Community Feed Visualization:} Reports in state $S_0 (\texttt{PendingValidation})$ are displayed on the public \ac{DApp} feed alongside an active countdown timer representing the 6-hour voting window.
    \item \textbf{Sybil-Resistant Vote Casting:} Citizens review the report and cast an upvote (\texttt{support = true}) or downvote (\texttt{support = false}) using an unused ticket nullifier.
    \item \textbf{Relayer Signature and Ticket Validation:} The relayer verifies the citizen's vote payload and forwards the transaction to \texttt{castValidationVote} on \texttt{Reporting.sol}.
    \item \textbf{On-Chain Vote Tallying:} The smart contract verifies that \texttt{usedValidationVoteNullifiers[reportId][voteNullifier]} is false, consumes the nullifier, and increments \texttt{validationUpvotes} or \texttt{validationDownvotes}.
    \item \textbf{State Finalization Engine:} State finalization occurs through two complementary mechanisms:
    \begin{itemize}
        \item \textit{Lazy Evaluation:} If any user submits a vote after the deadline ($\text{block.timestamp} > \texttt{phaseDeadline}$), the contract automatically invokes \texttt{\_finalizeSingleReport}.
        \item \textit{Automated Cron Finalization:} If no user action occurs, the relayer's background \texttt{CronService} invokes \texttt{batchFinalizeVotingWindows} daily at midnight, ensuring timely transitions.
    \end{itemize}
    If $\texttt{upvotes} > \texttt{downvotes}$, the report transitions to state $S_2 (\texttt{Open})$. Otherwise, it transitions to state $S_1 (\texttt{CommunityRejected})$.
\end{enumerate}

\subsection{Authority Resolution \& Action Workflow}
\label{subsec:authority-workflow}

Reports that achieve community consensus ($S_2 = \texttt{Open}$) become actionable for municipal authorities. Figure~\ref{fig:authority-action-workflow} details the authority resolution, work tracking, and status update workflow.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.95\textwidth,height=0.75\textheight,keepaspectratio]{Images/Chapter 3/authority_action_workflow.png}
    \caption{Authority Resolution and Infrastructure Repair Workflow}
    \label{fig:authority-action-workflow}
\end{figure}

The authority workflow executes through the following operations:
\begin{enumerate}
    \item \textbf{Dashboard Monitoring and Profile Verification:} Authorized municipal officials monitor validated reports via the authenticated Authority Dashboard in the \ac{DApp}. When an authority interacts with a report, their on-chain identity profile (\texttt{name}, \texttt{position}, \texttt{department}) managed by \texttt{AuthorityMultiSig.sol} is displayed to the community.
    \item \textbf{Work Initiation (\texttt{startWork}):} An authority claims an open issue by submitting a transaction calling \texttt{startWork(reportId, comment, imageCid)}. The smart contract verifies that the sender is currently authorized in \texttt{authorizedAuthorities} (governed exclusively by \texttt{AuthorityMultiSig.sol}), assigns the official to \texttt{report.assignedAuthority}, transitions the status to $S_3 (\texttt{InProgress})$, appends an \texttt{AuthorityAction} record to the on-chain audit log, and emits the \texttt{WorkStarted} event.
    \item \textbf{Progress Updates (\texttt{addAuthorityUpdate}):} While work is underway, the assigned authority can post mid-repair updates by calling \texttt{addAuthorityUpdate}. This appends explanatory comments and progress image \ac{CID}s to the audit history without altering the report state.
    \item \textbf{Resolution Declaration (\texttt{markAsSolved}):} Upon completing physical infrastructure repairs, the authority calls \texttt{markAsSolved(reportId, comment, imageCid)}, attaching photographic evidence of the repair. The contract transitions the report to $S_5 (\texttt{PendingVerification})$ and sets a new 6-hour community verification deadline.
    \item \textbf{Issue Rejection (\texttt{rejectIssue}):} If an authority determines that a report is duplicate, unfeasible, or out of jurisdiction, they call \texttt{rejectIssue(reportId, comment, imageCid)}. The contract transitions the status to $S_4 (\texttt{PendingRejectionReview})$, opening a 6-hour community appeal window.
\end{enumerate}

\subsection{Post-Resolution Verification \& Appeal Workflow}
\label{subsec:post-res-workflow}

The framework enforces mutual accountability by preventing authorities from unilaterally closing reports without citizen confirmation. Figure~\ref{fig:post-resolution-verification-workflow} illustrates the post-resolution verification and community appeal workflow.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.95\textwidth,height=0.75\textheight,keepaspectratio]{Images/Chapter 3/post_resolution_verification_workflow.png}
    \caption{Post-Resolution Verification and Community Appeal Workflow}
    \label{fig:post-resolution-verification-workflow}
\end{figure}

The post-resolution workflow governs two distinct review paths:
\begin{enumerate}
    \item \textbf{Repair Verification ($S_5 = \texttt{PendingVerification}$):}
    Citizens physically inspect the completed infrastructure repair and submit acceptance (\texttt{accept = true}) or rejection (\texttt{accept = false}) votes via \texttt{castVerificationVote} within the 6-hour window. Upon deadline finalization:
    \begin{itemize}
        \item If $\texttt{verificationAcceptVotes} \ge \texttt{verificationRejectVotes}$, the report transitions to the terminal state $S_6 (\texttt{Closed})$, marking successful resolution.
        \item If $\texttt{verificationRejectVotes} > \texttt{verificationAcceptVotes}$, the report transitions to $S_7 (\texttt{Reopened})$, signaling to municipal authorities that the repair was inadequate and requires corrective intervention.
    \end{itemize}
    \item \textbf{Rejection Review and Appeal ($S_4 = \texttt{PendingRejectionReview}$):}
    When an authority rejects an issue, citizens vote to uphold (\texttt{uphold = true}) or appeal (\texttt{uphold = false}) the rejection via \texttt{castRejectionReviewVote}. Upon deadline finalization:
    \begin{itemize}
        \item If $\texttt{rejectionUpholdVotes} \ge \texttt{rejectionAppealVotes}$, the rejection is sustained, and the report transitions to $S_6 (\texttt{Closed})$.
        \item If $\texttt{rejectionAppealVotes} > \texttt{rejectionUpholdVotes}$, the community appeal succeeds, and the report transitions to $S_7 (\texttt{Reopened})$, obligating the authority to re-examine the issue.
    \end{itemize}
\end{enumerate}

\subsection{Anonymous Public Opinion Polling Workflow}
\label{subsec:opinion-polling-workflow}

In addition to citizen-initiated issue reporting, the architecture supports top-down municipal consultation through an anonymous public opinion polling workflow managed by the \texttt{OpinionPolling.sol} smart contract. This workflow enables local governments to solicit democratic feedback on public works proposals, zoning changes, or budget allocations without compromising voter privacy.

The opinion polling workflow proceeds as follows:
\begin{enumerate}
    \item \textbf{Official Poll Creation:} An authorized municipal official calls \texttt{createOfficialPoll(ipfsMetadataCid, deadline, pollType)}, specifying an \ac{IPFS} \ac{CID} containing detailed proposal documentation, a timestamp deadline, and the poll modality (\texttt{TrueFalse} or \texttt{MultiChoice}). The smart contract verifies authority credentials against \texttt{Reporting.sol}'s access registry, assigns a unique \texttt{pollId}, and emits the \texttt{PollCreated} event.
    \item \textbf{DApp Poll Dissemination:} Active polls are displayed on the citizen \ac{DApp} interface, presenting proposal details fetched from \ac{IPFS} alongside selectable voting options.
    \item \textbf{Anonymous Ballot Casting:} A citizen selects an option index and generates an ephemeral voting request signed with an unused ticket nullifier. The relayer submits the transaction to \texttt{castVote(pollId, optionIndex, nullifier)}.
    \item \textbf{Sybil-Resistant Tallying:} The smart contract checks \texttt{nullifierVoted[pollId][nullifier]}. If unconsumed, it records the nullifier and increments \texttt{pollResults[pollId][optionIndex]}.
    \item \textbf{Poll Finalization:} Once the deadline elapses, any user or relayer can call \texttt{finalizePoll(pollId)} to mark the poll inactive and freeze results, providing municipal authorities with immutable, tamper-evident public consultation data.
\end{enumerate}

\section{Summary and Expected Outcomes}
\label{sec:summary-outcomes}

This chapter detailed the structural architecture, interface specifications, mathematical state modeling, two-tier multi-signature governance, and operational workflows of the decentralized local governance reporting framework. By integrating a six-layer topology with a hybrid on-chain/off-chain execution model, the system successfully addresses the core limitations of conventional centralized reporting systems.

The expected outcomes of the architectural design include:
\begin{enumerate}
    \item \textbf{Guaranteed Citizen Anonymity and Privacy:} Zero-knowledge authentication and single-use ticket nullifiers completely decouple real-world identity from on-chain transactions, removing fear of retaliation.
    \item \textbf{Decentralized Municipal Governance:} Replacing monolithic administrative control with \texttt{AuthorityMultiSig.sol} ensures that authority access and official identity profiles are governed democratically by a majority quorum of Super Admins.
    \item \textbf{Automated Off-Chain Orchestration:} The relayer's automated \texttt{AuthorityFundingService} and \texttt{CronService} eliminate manual treasury management and ensure deterministic batch finalizations of expired voting windows.
    \item \textbf{Tamper-Evident Accountability:} Storing metadata, state transitions, authority action logs, and voting tallies on a private \ac{PoA} blockchain ensures an immutable audit trail.
    \item \textbf{Automated Spam and Toxicity Mitigation:} The multi-oracle \ac{AI} Moderation Ensemble prevents abusive, irrelevant, or malicious content from polluting off-chain storage or ledger state.
    \item \textbf{Democratic Lifecycle Oversight:} Sybil-resistant community voting at validation, verification, and appeal stages prevents arbitrary dismissal of reports and enforces repair quality.
    \item \textbf{High Usability and Gasless Interaction:} The middleware relayer pattern eliminates cryptocurrency onboarding barriers, allowing citizens to engage via a responsive web application seamlessly.
\end{enumerate}

With the system architecture, mathematical state machine, governance topology, and workflows fully specified, Chapter 4 presents the technical realization and code-level implementation of each architectural component.
