\chapter{Testing and Performance Evaluation}
\label{ch:testing}

This chapter explains how the prototype has been tested. The system architecture and implementation are described in Chapters~\ref{ch:architecture} and~\ref{ch:implementation}. The tests have covered smart contracts, the relayer, AI moderation, IPFS, the identity simulator, the full reporting workflow, and blockchain performance. Test methods are separated from the discussion of their meaning, which is given in Chapter~\ref{ch:results}.

\section{Evaluation Aims and Questions}
\label{sec:evaluation-aims}

The evaluation has been guided by the following questions:

\begin{enumerate}
    \item Have the four smart contracts enforced their intended functions and access rules?
    \item Have duplicate actions, replay attempts, invalid signatures, and emergency-report abuse been rejected?
    \item Have the relayer, queue, AI services, IPFS service, and blockchain been integrated correctly?
    \item Have the recorded response time, throughput, block interval, and gas measurements been suitable for a prototype?
    \item Which claims can be supported by the available tests, and which claims still require wider evaluation?
\end{enumerate}

\subsection{Scope of Evidence}

Automated smart-contract tests and relayer unit and end-to-end tests are present in the project. AI API-security and classification test code and local logs are also present. However, AI benchmark result files have not been committed. The IPFS check is a manual integration script. The identity component is a simulator and has no automated test suite. No automated frontend tests are present.

The identity simulator issues government-signed ticket identifiers. It does not create or verify a real zero-knowledge proof. The AI component is an off-chain centralized aggregator that calls three classifier services. It is not a decentralized oracle network. CLIP-based civic image relevance is disabled. These limits have been treated as part of the evaluation scope.

\subsection{Security Test Procedure}

A used submission nullifier has been sent repeatedly. One hundred replay attempts are included in the security suite, and rejection has been expected for every attempt. Duplicate validation and verification votes have also been attempted with the same citizen pseudonym and a fresh nullifier. Duplicate poll votes have been attempted through nullifier reuse. Direct calls from a non-relayer account have been attempted. Emergency reclassification has been followed by another emergency submission before and after the 30-day penalty period.

The tests have checked controls against replay and simple duplicate participation. They have not proved resistance against every Sybil strategy. Their result depends on correct ticket issue by the trusted government simulator.

\section{Relayer Integration Testing}
\label{sec:relayer-testing}

The relayer has been tested at two levels. Unit tests have checked cryptographic validation. End-to-end tests have checked the HTTP request path and processing pipeline. A valid government ticket and citizen signature have been accepted. A forged government signature, a changed description, and a changed image have been rejected.

The BullMQ flow has been tested with AI moderation, IPFS upload, and blockchain submission as ordered steps. Failure has been introduced into IPFS and blockchain calls. Retries have been recorded after 2 seconds and 8 seconds, with failure after the third unsuccessful attempt. A relayer restart has also been introduced while work has been queued, and recovery from Redis has been checked.

Seven progress events have been expected in order, from \texttt{ai\_moderation\_in\_progress} to \texttt{completed}. Two concurrent citizens have been used in the recorded SSE isolation check. Only the related citizen's events have been received by each stream. SSE delivery latency has been recorded below 200\,ms in those cases. This is a recorded prototype result; the exact number of repeated latency observations has not been stated in the available text.

\section{AI Moderation Testing}
\label{sec:ai-testing}

\subsection{Method}

API-security and classification checks have been sent to the running centralized AI aggregator. Nine API cases have been used to cover valid access, missing or wrong API keys, a forged relayer signature, nonce replay, a timestamp older than 300 seconds, a file above 5\,MB, a PDF attachment, and more than three images.

Five recorded text samples have been used to cover a civic report, hate speech, commercial spam, non-civic personal text, and an emergency civic report. Four recorded image cases have been used to cover a safe image, corrupted image data, an unsafe image, and face blurring. Two poll descriptions have been used to check aggregator decisions. Three response checks have been used to check the decision and explanation fields.

\subsection{Recorded Outcomes and Limits}

All listed API-security cases and all listed classification examples have been recorded as passed. The safe civic and emergency text samples have been accepted. The hate, spam, and non-civic samples have been rejected. The corrupted and unsafe image samples have been rejected, and the face case has returned blurred media.

These values are recorded experiment findings supplied in the earlier report. They have not been independently reproduced from a committed benchmark result artifact. The sample is small and selected. Therefore, accuracy, precision, recall, fairness, and performance on Sinhala, Tamil, or broad real-world data cannot be concluded. Image safety and face handling have been checked, but civic image relevance has not been evaluated because the CLIP civic relevance feature is disabled.

\section{End-to-End Workflow Testing}
\label{sec:e2e-testing}

One recorded full lifecycle scenario has been executed. A signed ticket has been received by a simulated citizen. A report has then been submitted, seven ordered SSE events have been received, and the pending-validation report has been observed. Validation upvotes have been cast by three other simulated citizens. The voting window has been finalized, and the report has been moved to the open state. Work has been started by an authority, an update has been added, and the issue has been marked as solved. The resolution has been accepted by two simulated citizens, and the report has been moved to the closed state.

It has been shown by the scenario that the main services can work together for one selected successful path. It has not been a usability test, a browser compatibility test, or a large multi-user trial. No automated frontend suite has been used.

\section{Performance Evaluation Method}
\label{sec:performance-method}

\subsection{Measured Variables}

The benchmark script is designed to measure:

\begin{itemize}
    \item confirmed transactions per second (TPS);
    \item submit-to-confirm latency;
    \item the Clique block interval;
    \item gas used by report submission;
    \item gas used by voting; and
    \item gas used by batch finalization.
\end{itemize}

TPS has been measured by sending concurrent transactions and dividing the confirmed transaction count by elapsed time. Submit-to-confirm latency has been measured from transaction dispatch by the relayer to inclusion in a block. Block intervals have been read from consecutive block timestamps. Gas has been read from transaction receipts.

\section{Validity and Reproducibility Constraints}
\label{sec:evaluation-validity}

The evaluation has the following constraints:

\begin{itemize}
    \item Benchmark output files and AI benchmark artifacts are absent, so their recorded values cannot be reproduced from the repository alone.
    \item Some sample sizes and repetition counts have not been recorded.
    \item The AI samples are small and selected, so general classification quality cannot be estimated.
    \item IPFS has been checked by a manual script, and the identity simulator has no automated suite.
    \item No automated frontend tests, formal security proof, external penetration test, or production user study has been completed.
    \item The private network is small and controlled. Large public or municipal load has not been tested.
    \item Government ticket issue, the relayer, Redis, the AI aggregator, and the PoA validators remain trusted parts of the prototype.
\end{itemize}

These limits reduce external validity. The tests support prototype behaviour in the stated environment, but they do not prove production readiness.

\section{Chapter Summary}

Functional, security, integration, and performance checks have been described in this chapter. About 75 tests across Reporting, EmergencyReporting, Security, OpinionPolling, and AuthorityMultiSig areas are contained in the current contract inventory. Successful main workflows, rejection of tested replay and duplicate actions, relayer recovery, selected AI moderation outcomes, IPFS integrity, and a complete report lifecycle have been recorded. Performance values have been retained as recorded prototype results because raw benchmark outputs are not committed. Their meaning and the achievement of the project objectives are discussed in the next chapter.
